# Releasing

A release is a pushed tag. `.github/workflows/release.yml` does the rest: it runs the unit tests,
builds and signs both flavours, and publishes a GitHub Release with the artifacts attached.

## Cutting one

The version lives in exactly one place —
`build-logic/convention/src/main/kotlin/AndroidApplicationConventionPlugin.kt`:

```kotlin
private const val VERSION_NAME = "0.1.0"
```

So a release is two steps, in this order:

```bash
# 1. Bump VERSION_NAME, write the Play release notes (see "Google Play"), then commit both.
git commit -am "chore: 0.2.0"

# 2. Tag that commit and push both.
git tag v0.2.0
git push origin main v0.2.0
```

The tag must be the version with a `v` in front. The workflow's first step asks the build what
version it produces (`./gradlew -q :app:printVersionName`) and fails the release if the two
disagree, so tagging `v0.2.0` on a build that still says `0.1.0` stops there rather than publishing
four files whose names lie about their contents.

`versionCode` is not maintained by hand. It is computed from `versionName` — `0.1.0` is `100`,
`1.2.3` is `10203` — so it cannot drift out of step, and rebuilding a tag anywhere produces the
same number. That last part is the reason it is derived rather than taken from a CI counter:
F-Droid builds this repository itself.

A tag containing a hyphen (`v0.2.0-rc1`) is published as a pre-release. Its `versionCode` is the
same as the final `0.2.0`, so the release installs over its own candidate.

## What comes out

Both flavours, in both formats, named after the version:

| Asset | What it is |
|---|---|
| `plmail-0.2.0-foss.apk` | The build with no Google code in it. What most people want, and the one F-Droid tracks. |
| `plmail-0.2.0-google.apk` | FCM push, `de.pluetzner.plmail`, installable alongside the other. The build on Google Play. |
| `plmail-0.2.0-foss.aab` · `plmail-0.2.0-google.aab` | App bundles. Only the `google` one is any use for Play. |
| `plmail-0.2.0-*-mapping.txt` | R8 mapping files. |

Keep the mapping files. `isMinifyEnabled` is on for release builds, so a stack trace from a
published APK is unreadable without the mapping that produced it, and this is the only moment that
file is guaranteed to exist.

Release notes are generated by GitHub from the commits since the previous tag. Edit them afterwards
if the generated list is not the story you want to tell.

## Google Play

After the GitHub Release is published, `.github/workflows/play.yml` downloads
`plmail-<version>-google.aab` and its mapping file from it and uploads them to Google Play
(`de.pluetzner.plmail`) on the **beta** track, which is open testing and shows on Play as early
access. Pre-release tags are not uploaded: their `versionCode` equals the final release's, and Play
accepts each `versionCode` only once.

The texts live in `fastlane/metadata/android/<locale>/`, the layout F-Droid reads as well:

| File | What it is |
|---|---|
| `title.txt` · `short_description.txt` · `full_description.txt` | The store listing (30, 80 and 4000 characters at most). Sent to Play with every release. |
| `changelogs/<versionCode>.txt` | The release notes ("What's new", 500 characters at most), e.g. `changelogs/402.txt` for 0.4.2. |

The `en-US` release notes are required: without them the upload stops, so commit them before
tagging. Other languages are sent when their file exists.

Promoting a release from open testing to production is done in the Play Console. To upload an
older release, or to send one to another track, run the **Google Play** workflow by hand from
`main` with the tag and the track.

The upload uses a Google Cloud service account. It needs no roles in its Cloud project; its access
comes from the Play Console (Users and permissions), as app permissions for plMail only: view app
information, release to testing tracks, and manage store presence (for the listing), plus release
to production if the workflow should ever upload to that track. Its JSON key is the `PLAY_SERVICE_ACCOUNT_JSON` secret.

## Secrets

Five, set under **Settings → Secrets and variables → Actions**. Without the first four the release
fails loudly rather than quietly publishing something unsigned.

| Secret | What goes in it |
|---|---|
| `KEYSTORE_BASE64` | The release keystore, base64-encoded (see below). |
| `KEYSTORE_PASSWORD` | Password for the keystore itself. |
| `KEY_ALIAS` | Alias of the signing key inside it. |
| `KEY_PASSWORD` | Password for that key. |
| `PLAY_SERVICE_ACCOUNT_JSON` | The JSON key of the service account that uploads to Google Play (see above). |

To create a keystore, if there isn't one yet:

```bash
keytool -genkeypair -v -keystore plmail-release.jks -alias plmail \
    -keyalg RSA -keysize 4096 -validity 10000
```

Then, to put it in the secret:

```bash
base64 -w0 plmail-release.jks
```

Back it up somewhere that is not this repository and not a CI secret. Android identifies an app by
its signing key: lose it and the only way to ship an update is a new application id, which every
existing installation sees as a different app.

The workflow base64-decodes the keystore into the runner's temp directory, builds, and then checks
its own work with `apksigner verify` before anything is uploaded. That check is there because the
signing config is deliberately optional — see below — and an optional thing that silently did
nothing is exactly how unsigned APKs get published.

## Signing a release build locally

Rarely needed, but the same four values work off a properties file. Copy the template and fill it
in:

```bash
cp app/signing.properties.dist app/signing.properties
```

`app/signing.properties`, `*.jks` and `*.keystore` are all gitignored.

Without that file and without the environment variables, `./gradlew assembleRelease` still works —
it just produces `app-foss-release-unsigned.apk`. That fallback is deliberate: a contributor should
never need a signing identity to build the thing they are working on. The environment variables the
build reads are `PLMAIL_KEYSTORE_FILE`, `PLMAIL_KEYSTORE_PASSWORD`, `PLMAIL_KEY_ALIAS` and
`PLMAIL_KEY_PASSWORD` — named separately from the GitHub secrets so the build script's contract
does not depend on GitHub.
